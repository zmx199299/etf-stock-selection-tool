### 2026-04-06 (Night Session 2 - v0.0.9 五重修复)

**问题背景**：v0.0.8 发布后用户仍然报告"启动同步失败"。系统化调试 Phase 1 完成后，识别出 5 个根因。

**根因分析结果**：
v0.0.8 修复了 Python 引擎的启动崩溃，但前端启动流程本身仍有致命设计缺陷——`startupSync.ts` 在引擎启动后立刻发起 `sync_data`（全量数据同步），对于空数据库（首次安装）用户来说，这意味着要下载 500+ 基金的全部历史数据，耗时 30+ 分钟甚至超时失败。

**五重修复详情**：

#### Fix 1: startupSync.ts — 将 `sync_data` 改为 `ping`（最关键）
- **原问题**：前端 `ensureStartupSync()` 调用 `sync_data` RPC，触发全量同步
- **修复**：改为调用 `ping` 仅确认引擎存活，数据同步由 Python 后台线程自动完成
- **文件**：`src/utils/startupSync.ts`
- **错误提示文案更新**："同步失败，当前显示本地旧数据" → "引擎连接失败，当前显示本地旧数据"
- **影响范围**：同步更新 `FundList.vue`、`Dashboard.vue` 中的硬编码提示，改为使用 `startupSyncState.message`

#### Fix 2: engine.rs — 修复 BufReader 每次重建导致数据丢失
- **原问题**：`invoke()` 方法每次创建新 `BufReader::new(stdout)`，如果上一次调用的 BufReader 缓冲了额外数据，新 BufReader 会丢失
- **修复**：将 `BufReader<ChildStdout>` 作为 `EngineManager` 的持久字段，在 `start()` 时创建，`invoke()` 复用
- **文件**：`src-tauri/src/engine.rs`

#### Fix 3: main.ts — start_engine 失败时阻止后续 invoke_engine 调用
- **原问题**：`start_engine` 失败被 catch 吞掉后仍执行 `ensureStartupSync()` → `invoke_engine`，Rust 返回 "Engine is not running" 错误
- **修复**：新增 `setStartupSyncError()` API，`start_engine` 失败时直接设置错误状态，`ensureStartupSync()` 检测到 error 状态后跳过网络调用
- **文件**：`src/utils/startupSync.ts`、`src/main.ts`

#### Fix 4: main.py — 修复 SQLite 线程安全问题
- **原问题**：后台同步线程 `background_sync(db, source)` 与主 RPC 线程共享同一个 `db` 对象（同一个 SQLite 连接），SQLite 默认不支持多线程共享连接
- **修复**：`background_sync` 改为接收 `db_path`，内部创建独立的 `Database` 实例
- **文件**：`src-python/main.py`

#### Fix 5: 增加错误诊断信息传递
- **原问题**：Python stderr 在生产环境 GUI 应用中通过 `Stdio::inherit()` 输出，无终端时直接丢失
- **修复**：
  - 生产环境 Python stderr 重定向到 `~/.etf-analyzer/engine.log` 日志文件
  - 开发环境保持 `Stdio::inherit()` 输出到终端
  - 新增 `dirs` crate 依赖用于获取 home 目录
- **文件**：`src-tauri/src/engine.rs`、`src-tauri/Cargo.toml`

**新增/修改测试**：
- `src/utils/__tests__/startupSync.spec.ts`：更新 2 个测试（ping 替代 sync_data），新增 2 个测试（setStartupSyncError）

## v0.0.15 三重修复 — WAL 并发锁 / em 源跳过 / 部分同步重试 (2026-04-09)

### 问题来源
用户 Windows 安装 v0.0.14 后日志 (`C:\Users\zmx19\.etf-analyzer\engine.log`) 暴露三个问题：

### Fix 1: SQLite "database is locked" — WAL 模式
- **问题**：后台同步线程和 RPC 主线程同时写入 SQLite，默认 journal_mode=delete 只允许单写，导致 `database is locked`
- **修复**：`Database.init()` 中执行 `PRAGMA journal_mode=WAL`，启用 Write-Ahead Logging
- **效果**：允许并发读写，后台同步和用户操作互不阻塞
- **文件**：`src-python/engine/models/database.py:13`
- **新增测试**：`test_wal_mode_enabled_after_init`、`test_concurrent_writes_no_database_locked`

### Fix 2: em 数据源连续失败跳过
- **问题**：东方财富 API 持续不可用，每只基金都浪费 ~1s 超时再 fallback 到新浪，1754 只基金多浪费 ~30 分钟
- **修复**：`AkshareSource` 新增 `_em_consecutive_failures` 计数器和 `em_skip_threshold`（默认 5），连续失败达阈值后跳过 em 直接用 sina
- **效果**：同步时间从 ~60min 降至 ~30min（只有 sina 的纯数据获取时间）
- **文件**：`src-python/engine/data/akshare_source.py`
- **新增测试**：`test_skips_em_after_consecutive_failures`、`test_em_success_resets_failure_counter`、`test_em_skip_threshold_configurable`

### Fix 3: 后台同步部分失败后的重试检测
- **问题**：后台同步在处理 500/1754 只基金时崩溃（Fix 1 的 locked 错误），下次重启 `has_daily_quotes()` 返回 True 导致不重试

- **main.py** 改用 `needs_background_sync()` 替代 `not has_daily_quotes()`
- **文件**：`src-python/engine/models/database.py`、`src-python/main.py`
- **新增测试**：4 个覆盖率场景测试
