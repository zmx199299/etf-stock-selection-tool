# 启动先同步数据与 Windows MSI 命名修正设计

## 背景

当前已完成 `v0.0.4` 的三平台发布，但用户在实际安装与运行中发现两个问题：

1. Windows 安装包文件名为 `ETF.Analyzer_0.0.4_x64_en-US.msi`，用户希望去掉 `en-US` 后缀。
2. 打开软件后，数据不会自动更新。

经过代码核查：

- Windows 产物命名当前来自 Tauri/WiX 默认生成的 MSI 文件名，workflow 直接上传原始产物，没有做重命名处理。
- Python 后端已注册 `sync_data` 方法，但前端当前只调用 `get_dashboard_signals` 和 `get_fund_list`，没有任何地方在应用启动时触发全量同步。

因此，这两个问题都属于当前实现缺失，而不是偶发运行错误。

## 目标

1. GitHub Release 中上传的 Windows 安装包文件名去掉 `en-US` 后缀，改为 `ETF.Analyzer_<version>_x64.msi`。
2. 应用启动后自动先执行一次全量同步，再进入数据读取流程。
3. 如果启动同步失败，允许进入页面，并明确提示“同步失败，显示本地旧数据”。
4. 通过测试约束启动同步顺序，避免后续再次退化为“直接读取旧数据”。

## 非目标

1. 不在本次处理中深挖或重构 Tauri/WiX 的底层语言与文化配置。
2. 不在本次处理中设计独立的同步引导页或复杂进度 UI。
3. 不在本次处理中加入手动同步按钮、定时同步器或后台增量同步策略。

## 现状与根因

### 1. Windows MSI 命名

- `.github/workflows/release.yml` 当前直接上传 `src-tauri/target/<target>/release/bundle/msi/*.msi`
- Windows bundler 生成的文件名自带 `en-US`
- 当前没有上传前重命名步骤，因此 release 中直接展示原始文件名

### 2. 启动不同步数据

- Python 服务已注册：`sync_data -> DataSyncPipeline.sync_all()`
- Dashboard 页面当前只调用 `get_dashboard_signals`
- FundList 页面当前只调用 `get_fund_list`
- 前端没有统一的“应用启动同步”状态管理层
- 因此页面实际表现为：直接读取当前数据库已有内容；数据库若没更新，UI 也不会更新

## 方案比较

### 方案 A：最小改动修复（推荐）

做法：

1. 在 workflow 的 Windows 上传阶段，把原始 `*_x64_en-US.msi` 复制或重命名为 `*_x64.msi` 后再上传。
2. 在前端增加统一的“启动同步状态”模块。
3. 应用启动时先调用一次 `sync_data`，结束后再加载页面数据。
4. 同步失败时允许进入页面，并展示失败提示。

优点：

- 改动最小，风险低。
- 不干扰已跑通的 Windows bundler 行为。
- 能精确满足当前用户诉求。

缺点：

- MSI 原始文件名内部仍可能带 `en-US`，只是最终上传到 release 的文件名不再带该后缀。

### 方案 B：底层修改 Windows installer 文化配置

做法：尝试从 Tauri/WiX 配置层移除或改变 `en-US` 文化后缀。

优点：

- 从源头修正命名。

缺点：

- 需要额外研究 Tauri/WiX 打包细节。
- 有更高概率引入新的 Windows 发布回归。

### 方案 C：增加独立同步启动页

做法：启动后先进入专门的同步页面，显示状态、进度和重试入口。

优点：

- 用户感知最清晰。

缺点：

- 超出本次最小需求，改动面偏大。

## 最终设计

采用方案 A。

## 设计细节

### 1. Windows 安装包命名处理

修改 `.github/workflows/release.yml` 的 Windows 上传阶段：

1. 先定位构建出的原始 MSI 文件。
2. 按版本号生成新的目标文件名：`ETF.Analyzer_<version>_x64.msi`
3. 将原文件复制或重命名为新文件名。
4. GitHub Release 只上传新文件名。

这样不改变 Tauri 实际 bundler 行为，只改变最终用户看到的下载文件名。

### 2. 前端启动同步流程

新增一个统一的前端启动同步状态模块，负责：

- 记录当前状态：`idle` / `syncing` / `success` / `error`
- 在生产环境调用 `invoke_engine(method: 'sync_data')`
- 保存失败提示信息，供页面展示
- 保证一次应用启动只执行一次同步流程，避免 Dashboard 和 FundList 各自重复触发

### 3. 页面数据加载顺序

应用行为改为：

1. 页面挂载
2. 先确保启动同步流程执行
3. 同步结束后：
   - 成功：读取真实数据库数据
   - 失败：提示失败，并继续读取当前本地已有数据；若读取失败则继续走现有 mock 回退

### 4. 页面展示要求

不新增复杂同步页，只做轻量反馈：

- 同步中：页面可以显示简单的“正在同步数据”文案或加载态
- 同步失败：页面显示“同步失败，当前显示本地旧数据”之类提示
- 同步成功：不额外打扰用户

### 5. 影响范围

预计会涉及：

- `.github/workflows/release.yml` — Windows 上传前重命名 MSI
- 前端共享数据加载层（如 `src/utils/dashboardSignals.ts`）
- 基金列表页数据加载逻辑
- 新增一个前端启动同步状态模块或工具文件
- 对应前端测试文件

### 6. 测试设计

按 TDD 执行。

需要覆盖：

1. 启动时先执行同步，再读取 Dashboard 数据。
2. 启动时先执行同步，再读取 FundList 数据。
3. 同步失败时页面仍可进入，并显示失败提示。
4. workflow 中 Windows 上传步骤使用去掉 `en-US` 的目标文件名。

### 7. 风险与控制

1. 启动同步可能较慢。
   - 控制：只做一次启动同步，避免页面重复触发。
2. 同步失败可能影响用户感知。
   - 控制：允许进入页面并明确提示，而不是卡死在加载态。
3. Windows 重命名如果写死版本号，后续发版容易出错。
   - 控制：从构建产物或 tag 动态生成目标文件名。

## 验收标准

1. Release 中 Windows 安装包名称不再包含 `en-US`。
2. 正式运行桌面应用时，启动后会先调用一次 `sync_data`。
3. Dashboard / FundList 读取真实数据前，已完成这次启动同步。
4. 同步失败时，页面会提示失败并继续显示本地旧数据。
5. 前端测试与构建验证通过，发布流程可继续成功产出三平台安装包。
